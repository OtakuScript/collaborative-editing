# Markdown 协同编辑平台 V1 技术方案

## 1. 文档定位

本文档只描述 V1 的技术实现方案，包括技术栈、服务边界、数据模型、文件存储、实时协同、API、前后端实现约定和部署方式。

项目目标、功能范围、用户角色和核心用户流程见 `V1 项目方案.md`。

## 2. 技术架构

### 2.1 技术栈

前端：

- `React 18`
- `TypeScript`
- `Vite`
- `React Router`
- `TanStack Query`
- `Zustand`
- `Ant Design`
- `Tiptap`
- `Yjs`

后端：

- `NestJS`
- `Prisma`
- `PostgreSQL`

实时协作：

- `Hocuspocus`
- `Yjs`

文件存储：

- 服务端本地目录或 Docker 挂载目录。
- 每篇文档保存为一个真实 `.md` 文件。

部署：

- `Docker Compose`

### 2.2 服务拆分

V1 拆成 3 个服务：

- `web-app`：前端单页应用，负责登录、工作区、文档列表和编辑器界面。
- `api-service`：后端 REST API，负责认证、权限、工作区、成员、文档元信息、文件路径生成和文档访问授权。
- `collab-service`：实时协作服务，负责 Yjs 文档同步、在线状态、正文加载、正文保存触发和协同状态持久化。

V1 不需要：

- `worker-service`
- `BullMQ`
- `Redis`
- `MinIO`

如果后续需要异步任务、缓存、附件或大规模 presence，再单独引入。

### 2.3 架构边界补充方案

V1 的三服务拆分用于隔离页面体验、业务事实和协同运行时，不引入额外分布式复杂度。服务边界遵守 `第一轮施工计划/工作清单/08-架构边界与ADR.md` 中的补充方案和 ADR-001。

核心协作关系：

```text
web-app
  -> api-service: 登录、工作区、成员、文档元信息、文档访问校验
  -> collab-service: 文档协同连接和实时编辑

collab-service
  -> api-service: 内部文档访问校验，获取 readonly、role、filePath
  -> data/storage: 基于授权后的 filePath 读取和保存 Markdown 正文

api-service
  -> PostgreSQL: 用户、工作区、成员、文档元信息
```

边界原则：

- `api-service` 是业务事实来源，拥有认证、权限、工作区、成员、文档元信息和文件路径生成规则。
- `collab-service` 是协同运行时，拥有 Yjs 房间、连接状态、协同状态同步和后续正文保存触发。
- Markdown 文件路径只能由 `api-service` 生成和授权。
- Markdown 正文运行时加载和保存由 `collab-service` 执行，但必须基于 `api-service` 的授权结果。
- 权限规则只在 `api-service` 实现，`collab-service` 通过内部接口消费授权结果。
- `packages/shared` 只承载类型和契约，不承载业务实现。

关键流程：

1. 创建文档时，`web-app` 调用 `api-service`；`api-service` 校验权限、创建 `Document` 记录、生成 `file_path` 并初始化 `.md` 文件。
2. 打开文档时，`web-app` 先请求 `api-service` 获取文档元信息，再使用 token 和 `documentId` 连接 `collab-service`。
3. 建立协同连接时，`collab-service` 调用 `api-service` 的内部文档访问校验能力，获取 `allowed`、`readonly`、`role` 和 `filePath`。
4. 保存文档时，`collab-service` 监听 Yjs 变化，debounce 后序列化为 Markdown，并基于授权后的 `filePath` 原子写入 `.md` 文件。

### 2.4 架构决策记录

完整 ADR 独立维护在 `ADR/` 目录。

- `ADR/ADR-001-服务边界与Markdown文件所有权.md`

## 3. 数据模型

V1 数据库只保存用户、工作区、成员关系和文档元信息。文档正文以 `.md` 文件形式保存，不直接存入数据库。

### 3.1 User

字段建议：

- `id`
- `email`
- `password_hash`
- `display_name`
- `created_at`
- `updated_at`

约束：

- `email` 全局唯一。
- 密码只保存 hash，不保存明文。

### 3.2 Workspace

字段建议：

- `id`
- `name`
- `owner_id`
- `created_at`
- `updated_at`

约束：

- `owner_id` 指向 `User.id`。

### 3.3 WorkspaceMember

字段建议：

- `id`
- `workspace_id`
- `user_id`
- `role`
- `created_at`
- `updated_at`

角色枚举：

- `owner`
- `editor`
- `viewer`

约束：

- 同一个用户在同一个工作区内只能有一条成员记录。
- `role` 决定该用户对工作区和文档的操作权限。

### 3.4 Document

字段建议：

- `id`
- `workspace_id`
- `title`
- `file_path`
- `created_by`
- `created_at`
- `updated_at`

说明：

- `file_path` 保存服务端 `.md` 文件的相对路径。
- `title` 用于页面展示，默认也用于生成初始文件名。
- 文档正文不进入 `Document` 表。

## 4. Markdown 文件存储方案

Markdown 文件的安全边界由 `api-service` 决定，运行时读写由 `collab-service` 执行。

- `api-service` 负责生成和保存 `Document.file_path`。
- `api-service` 负责判断用户是否能访问、编辑或管理文档。
- `collab-service` 只能使用 `api-service` 返回的文档授权结果和文件路径。
- 客户端不得传入文件系统路径。
- `data/storage` 只承载 Markdown 正文文件，不承载数据库、缓存或临时业务数据。
- 运行时只有 `collab-service` 需要直接读写 `data/storage`。
- `api-service` 只负责授权和文件路径规则，不直接接触正文写入流程。
- `web-app` 不挂载也不直接访问 `data/storage`。

### 4.1 文件目录

服务端统一管理 Markdown 文件，建议目录结构：

```text
storage/
  workspaces/
    {workspaceId}/
      documents/
        {documentId}.md
```

示例：

```text
storage/workspaces/ws_001/documents/doc_001.md
```

数据库中的 `Document.file_path` 保存相对路径：

```text
workspaces/ws_001/documents/doc_001.md
```

### 4.1.1 `Document.file_path` 生成规则

路径格式固定为：

```text
workspaces/{workspaceId}/documents/{documentId}.md
```

规则：

- `workspaceId` 使用数据库中的工作区 id。
- `documentId` 使用数据库中的文档 id。
- 文件名永远使用 `{documentId}.md`，不使用文档标题生成文件名。
- 重命名文档只修改 `Document.title`，不修改 `Document.file_path`。
- `Document.file_path` 是相对于 `STORAGE_ROOT` 的相对路径，数据库中不保存绝对路径。
- 创建文档时由 `api-service` 生成并保存 `file_path`。
- `collab-service` 只能使用 `api-service` 授权结果中的 `filePath`，不能自行拼接来自客户端的路径。

删除策略：

- V1 默认采用硬删除：删除文档时删除 `Document` 记录，并删除对应 `.md` 文件。
- 删除必须先完成权限校验。
- 删除文件失败时，接口不能静默成功，需要返回错误或记录待清理状态。

路径安全规则：

- 禁止客户端传入文件路径。
- 禁止 `..`、绝对路径、盘符路径和 URL 形式路径。
- 读写前必须把 `STORAGE_ROOT + filePath` 解析为规范化路径，并确认结果仍在 `STORAGE_ROOT` 内。
- 路径安全规则需要覆盖单元测试。

### 4.2 创建文档

创建文档流程：

1. 用户在文档列表页点击新建文档。
2. 前端提交文档标题。
3. `api-service` 校验用户是否是该工作区的 `owner` 或 `editor`。
4. 后端创建 `Document` 记录。
5. 后端生成 `Document.file_path`，并初始化对应 `.md` 文件。
6. 初始文件内容可以为空，也可以写入一级标题。
7. 真实 `.md` 文件由 `collab-service` 在运行时通过授权后的路径读取和写入。

初始内容示例：

```md
# 新文档
```

### 4.3 打开文档

打开文档流程：

1. 前端进入 `/documents/:documentId`。
2. 前端请求文档元信息。
3. 后端校验用户是否有访问权限。
4. 前端建立协同连接。
5. `collab-service` 调用 `api-service` 的内部校验能力，获取授权结果和 `file_path`。
6. 如果当前协同房间尚未初始化，则读取 `.md` 文件并转换为编辑器初始内容。
7. 用户进入编辑器后看到所见即所得内容。
8. `collab-service` 只通过授权后的相对路径访问 `data/storage`，不接受客户端传入的绝对路径或自定义目录。

### 4.4 保存文档

保存文档不由每个客户端直接写文件，而由服务端统一处理。

保存规则：

- 多人编辑时，同步的是 Yjs 协同状态。
- `collab-service` 监听文档变化。
- 文档变化后 debounce 保存，例如 2 到 5 秒内没有新的变化再写入文件。
- 保存时将编辑器内容序列化为 Markdown。
- 写文件时使用同一文档维度的串行写入，避免并发覆盖。
- 保存成功后更新 `Document.updated_at`。
- 写入路径必须来自 `api-service` 授权结果，不能由客户端或前端决定。

### 4.5 文件写入安全

必须遵守：

- 不允许客户端传入任意文件路径。
- 文件路径只能由后端根据 `workspaceId` 和 `documentId` 生成。
- 删除文档时先校验权限，再删除数据库记录和对应 `.md` 文件。
- 写入文件时使用临时文件加原子替换，降低写入中断导致文件损坏的概率。

推荐写入流程：

1. 将 Markdown 内容写入 `{documentId}.md.tmp`。
2. 写入完成后替换 `{documentId}.md`。
3. 替换成功后删除临时文件。

### 4.6 自动保存失败处理

自动保存由 `collab-service` 负责，失败时不能把状态误报为已保存。

失败处理规则：

- 写入失败时，保留当前 Yjs 文档内存状态。
- 对同一文档按顺序重试，避免多个保存任务并发覆盖。
- V1 默认重试 3 次，建议退避间隔为 1 秒、3 秒、5 秒。
- 重试仍失败时，文档保存状态标记为 `save_failed`。
- 前端应显示保存失败状态，并提示用户不要关闭页面或稍后重试。
- `Document.updated_at` 更新失败时，不影响 `.md` 文件已经写入的事实，但必须记录错误并在后续补偿。
- 服务重启会丢失尚未落盘的内存状态，因此自动保存失败时必须向前端暴露明确状态。

建议保存状态：

- `idle`：无待保存变更。
- `saving`：正在保存。
- `saved`：已保存。
- `save_failed`：保存失败，需要用户感知。

## 5. 实时协同方案

### 5.1 协同房间

每篇文档对应一个协同房间：

```text
document:{documentId}
```

前端连接 `collab-service` 时携带：

- `documentId`
- 用户身份 token

服务端连接校验：

- token 是否有效。
- 用户是否存在。
- 用户是否属于该文档所在工作区。
- 用户角色是否允许查看。
- 如果用户是 `viewer`，协同连接只能以只读方式进入。

### 5.2 协同数据

编辑器使用 Tiptap + Yjs。

基本原则：

- 编辑器状态不复制到全局 store。
- 协同正文以 Yjs 文档为准。
- 页面 UI 状态可以放在 Zustand，例如侧栏开关、当前连接状态、当前在线成员。
- 服务端 `.md` 文件是持久化结果，不是多人协同过程中的直接写入对象。

### 5.3 在线状态

在线状态使用 Yjs awareness。

在线成员展示信息：

- 用户 id。
- 用户昵称。
- 用户颜色。
- 当前连接状态。

V1 只要求展示当前在线成员，不要求显示精确光标位置。如果编辑器集成成本可控，可以展示协同光标；如果实现复杂，则放到后续版本。

### 5.4 断线重连

断线重连要求：

- 前端显示连接中、已连接、已断开状态。
- 短暂断线后自动重连。
- 重连后从协同服务同步最新状态。
- 保存状态不能误报为已保存。

### 5.5 viewer 只读协同控制

`viewer` 只读不能只依赖前端禁用编辑器。前端禁用只能改善用户体验，真正的写入限制必须在 `collab-service` 层执行。

规则：

- `collab-service` 建立连接前调用内部文档访问校验接口。
- 当返回 `readonly=true` 时，该连接只能接收文档更新和 awareness 信息。
- `readonly=true` 的连接不能向 Yjs 文档提交内容更新。
- 如果只读连接发送写入更新，`collab-service` 必须拒绝该更新，并记录安全日志。
- `owner` 和 `editor` 可以提交正文更新。
- `viewer` 可以看到文档变化和在线状态，但不能修改正文。

测试要求：

- 前端只读模式下不能编辑。
- 伪造 WebSocket 更新时，`collab-service` 仍能拒绝 viewer 写入。
- viewer 不影响 editor 的正常协同编辑。

## 6. API 设计

接口细节独立维护在 `V1 接口文档.md`。

技术方案只保留 API 边界原则：

- REST API 由 `api-service` 提供，负责认证、工作区、成员和文档元信息。
- 文档正文由 `collab-service` 通过协同协议加载和保存。
- V1 不提供独立的正文保存 REST API。
- `collab-service` 建立协同连接前必须调用内部文档访问校验接口。

## 7. 前端实现约定

### 7.1 目录结构

建议目录：

```text
src/
  app/
    router/
    providers/
    layouts/
  features/
    auth/
    workspace/
    document/
    editor/
  entities/
    user/
    workspace/
    document/
  shared/
    api/
    components/
    hooks/
    styles/
    utils/
```

### 7.2 状态分工

`TanStack Query` 负责：

- 当前用户信息。
- 工作区列表。
- 文档列表。
- 文档元信息。
- 成员列表。
- 服务端请求缓存和失效。

`Zustand` 负责：

- 当前编辑页 UI 状态。
- 连接状态。
- 在线成员展示数据。
- 本地弹窗和面板状态。

Tiptap/Yjs 负责：

- 编辑器正文。
- 协同同步。
- undo/redo 编辑历史。

不要把编辑器正文复制一份到 Zustand 或 React state。

### 7.3 编辑器能力

V1 编辑器必须支持：

- 一级到三级标题。
- 段落。
- 有序列表。
- 无序列表。
- 引用块。
- 加粗。
- 斜体。
- 行内代码。
- 代码块。
- 链接。
- 表格。

V1 可以暂不支持：

- 图片上传。
- Mermaid。
- 数学公式。
- 目录自动生成。
- 复杂嵌套块。

### 7.4 Markdown 转换

编辑器内部可以使用 Tiptap 的结构化文档模型，但持久化结果必须是 Markdown。

转换要求：

- 打开文档时：Markdown 转编辑器内容。
- 保存文档时：编辑器内容转 Markdown。
- 常用 Markdown 结构往返转换后不能明显丢失。

需要重点验证：

- 标题层级。
- 列表嵌套。
- 代码块语言。
- 表格。
- 链接。
- 引用块。

## 8. 后端实现约定

### 8.1 认证

认证采用 JWT。

要求：

- 密码使用 bcrypt 或 argon2 hash。
- 登录成功返回 access token。
- 前端请求 API 时携带 token。
- 后端通过 guard 校验 token。
- 协同服务连接时也必须校验 token。

### 8.2 权限校验

权限校验统一封装，不在各个 controller 中散落实现。

建议提供方法：

- `canViewDocument(userId, documentId)`
- `canEditDocument(userId, documentId)`
- `canManageWorkspace(userId, workspaceId)`

所有文档 API 和协同连接都必须经过权限校验。

权限规则只在 `api-service` 中实现：

- REST API 请求由 `api-service` 自己校验。
- WebSocket 连接由 `collab-service` 调用 `api-service` 的内部校验能力。
- `collab-service` 不直接判断 workspace membership 规则，只消费校验结果。

建议内部校验返回最小结构：

```ts
type DocumentAccessResult = {
  allowed: boolean;
  readonly: boolean;
  documentId: string;
  workspaceId: string;
  filePath: string;
  role: 'owner' | 'editor' | 'viewer';
};
```

### 8.3 文件服务

文件路径和安全规则由 `api-service` 拥有。文件服务负责：

- 根据 `workspaceId` 和 `documentId` 生成文件路径。
- 创建初始 `.md` 文件。
- 为协同服务提供经过授权的相对文件路径。
- 删除 `.md` 文件。

文件服务禁止：

- 使用用户传入路径直接读写文件。
- 允许 `../` 这类路径穿越。
- 将正文内容写入数据库替代 `.md` 文件。

### 8.4 协同服务

协同服务负责：

- 建立文档房间。
- 通过 `api-service` 校验连接用户的文档访问权限。
- 初始化 Yjs 文档。
- 基于授权后的 `file_path` 读取 Markdown 正文。
- 同步多人编辑。
- 维护 awareness 在线状态。
- 将 Yjs 文档序列化为 Markdown。
- debounce 保存到授权后的 `.md` 文件。

协同服务不负责：

- 用户注册登录。
- 工作区创建。
- 文档元信息 CRUD。
- 权限规则实现。
- 文件路径生成。

## 9. 共享包边界

`packages/shared` 只放跨应用稳定契约：

- DTO 类型。
- 枚举。
- API 路由常量。
- WebSocket 房间命名规则。
- 环境变量 schema 类型。
- 前后端都需要理解的错误码。

`packages/shared` 禁止放：

- Prisma client。
- 数据库访问逻辑。
- NestJS service / controller。
- React 组件。
- 文件系统读写逻辑。
- 权限规则实现。
- Hocuspocus / Yjs 运行时代码。

## 10. 部署方案

Docker Compose 至少包含：

- `web-app`
- `api-service`
- `collab-service`
- `postgres`

建议挂载目录：

```text
./data/postgres
./data/storage
```

挂载边界：

- `./data/postgres` 只作为 PostgreSQL 数据目录。
- `./data/storage` 只作为 Markdown 正文目录。
- `./data/storage` 只挂载给 `collab-service`，因为它负责正文读取和保存。
- `api-service` 不直接挂载 `./data/storage`，它只负责授权和文件路径生成。
- `web-app` 不挂载 `./data/storage`。
- `postgres` 不与 `./data/storage` 混用。

环境变量：

```text
DATABASE_URL=postgresql://...
JWT_SECRET=...
STORAGE_ROOT=/app/storage
WEB_PORT=5173
API_PORT=3000
COLLAB_PORT=1234
POSTGRES_PORT=5432
API_INTERNAL_BASE_URL=http://api-service:3000
COLLAB_WS_URL=ws://collab-service:1234
```

本地开发端口建议：

- `web-app`: `5173`
- `api-service`: `3000`
- `collab-service`: `1234`
- `postgres`: `5432`

以上端口是默认开发端口，不表示本机一定空闲。如果端口被占用，可以修改对应的 `WEB_PORT`、`API_PORT`、`COLLAB_PORT`、`POSTGRES_PORT`，并同步修改 `DATABASE_URL`、`API_INTERNAL_BASE_URL`、`COLLAB_WS_URL`、前端 API 地址和前端协同 WebSocket 地址。

## 13. 后续扩展方向

V1 完成后，可以按实际需求选择扩展：

- 历史版本：基于快照表或 Git 实现。
- 评论审阅：在文档位置上绑定评论。
- Agent 能力：基于当前 Markdown 内容做总结、润色或生成建议。
- Git 同步：将工作区文档映射到 Git 仓库。
- 附件和图片：引入对象存储。
- Markdown 源码模式：提供源码编辑和所见即所得切换。
- 导出能力：导出 HTML、PDF 或压缩包。
- 企业登录：接入 SSO 或 LDAP。

后续扩展不能影响 V1 的核心原则：文档正文以 Markdown 文件为最终持久化结果，协同编辑通过 Yjs 统一管理实时状态。
